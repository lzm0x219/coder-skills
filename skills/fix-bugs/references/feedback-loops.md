# 构建缺陷反馈循环

在 `fix-bugs` 的 S1 使用。根据症状选能经过真实故障路径的入口；表中的红灯判断用于检查具体循环是否捕捉了用户的问题。

| 症状与入口 | 可操作的循环 | 红灯判断与稳定化 |
| --- | --- | --- |
| 已有失败测试 | 先运行最窄的相关测试；若它只测内部函数，补跑用户调用入口。 | 断言用户可见结果，保留失败断言和输入；固定测试数据。 |
| 函数、库或 SDK 的错误结果 | 用最小调用夹具传入相同参数，比较返回值、错误类别和副作用。 | 不能只断言进程退出码；固定依赖实现和版本。 |
| CLI 或文件处理 | 保存脱敏的输入夹具，运行同一命令，比对输出文件、标准输出与退出码。 | 用语义断言或稳定快照，排除时间戳、路径等无关差异。 |
| HTTP/RPC 服务 | 对本地或获准的测试实例发出同一请求，检查状态、响应体及必要的状态变化。 | 固定身份、请求体和初始状态；不要向真实服务反复写入。 |
| UI 行为 | 用浏览器脚本操作实际入口，检查 DOM、网络或可见结果；不能自动化时用 `../scripts/hitl-loop.sh` 固定人工步骤。 | 同时保存操作和观察点；不要把截屏存在等同于行为正确。 |
| 线上独有的请求或事件 | 使用脱敏的请求、trace 或事件在隔离环境回放；无法回放时核对日志与版本差异。 | 保留顺序、身份和时间相关字段；回放不得指向生产副作用。 |
| 偶发、竞态或顺序问题 | 在可重复的安全夹具上按相同条件多次运行，可用 `../scripts/repro-rate.py` 计数；再逐个改变并发、延时或顺序，必要时缩短触发窗口。 | 记录红灯次数/总次数、超时次数与条件；修复前后使用可比的条件，单次通过无效。若修复改变进程启动或信号处理，还要验证被启动程序仍能接收原有信号。 |
| 只在某次变更后出现 | 用同一个红/绿判定比较已知好坏版本、配置或数据；判定足够自动化时再二分。 | 每个被比较状态都运行同一检查，避免构建或环境差异伪装成代码回归。 |
| 性能退化 | 先确定用户受影响的时延/资源指标及可判红的预算或已知正常基线；固定输入、机器/配置和预热方式，重复测量并记录中位数、尾部与波动，再用 profiler 或查询计划定位。 | 修复前后按同一采样方案比较；改善须超过测量波动，且原始慢场景也改善。单次计时或日志量不能证明修复。 |
| 输入空间过大 | 从一个真实失败例子出发做属性测试、生成或差分检查，并保留随机种子与最小反例。 | 断言明确不变量；生成数据不可代替原始场景的最终复测。 |

以下示例从 Skill 目录执行。人工复现：`bash scripts/hitl-loop.sh "导出时报错" "打开测试环境并登录" "点击导出"`，脚本逐步等待操作，输出脱敏观察；退出码 1 表示红灯，0 表示绿灯，3 表示无法判断，2 表示输入不完整。间歇故障计数：`python3 scripts/repro-rate.py --runs 30 --timeout 10 -- <安全且可重复的检查命令>`。先单独确认命令的非零退出确实是**同一症状**，再计数；返回值分布用于识别检查程序自身出错。计数器自身退出码为 0 只表示采样执行成功，`red` 才是非零退出次数；只对无外部副作用的检查重复采样。
