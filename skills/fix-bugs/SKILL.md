# 修复缺陷

以用户症状为验收对象。按 S0→S7 的证据状态推进；已有可信证据可满足对应状态的退出条件。用现有 issue 或工作记录保留 `状态｜命令或操作｜观察｜下一次实验`，每次回退也更新它。只读诊断不进入修复状态。

## S0 界定故障

记录实际与期望行为、触发输入、版本/环境及影响范围。读取项目约束、相关实现和检查入口；有 `CONTEXT.md` 或相关 ADR 时一并读取。**进入 S1：**能明确判定同一症状何时出现、何时消失。缺少关键事实时先从仓库与现有输出补证，仍缺失才索取最小必要信息。

## S1 建立红灯

若开始时没有可直接运行的红灯，先读[反馈循环操作表](references/feedback-loops.md)选择入口；人工操作、偶发采样和性能测量也读对应行。运行用户给出的复现或项目已有检查，记录可重跑的命令/步骤、输入、预期与实际输出。捕获或回放前脱敏凭据与个人数据，凭据经环境变量或安全存储传入；脱敏若抹去故障信号，记录缺失证据并索取可安全使用的样本。**红灯**必须经过故障路径，因用户所述症状失败；检查至少实际运行一次。固定时间、随机数、数据和配置，使诊断循环可重复且足够快。原场景较慢时另保留快循环，S6 仍复测原场景。**进入 S2：**已观察到同一症状的红灯。

**无红灯：**核对版本、输入、配置、权限、时序与环境，寻找脱敏日志、trace 或请求样本。若源码和明确不变量能独立证明另一个缺陷，先建立对该不变量变红的替代检查，再转 S4 核实；用户原症状保持「未复现」，最终只能有限交付。没有红灯也没有独立证据时，报告已试入口与缺失证据，停在 S1。

## S2 缩小反例

从原场景每次删减一个输入、步骤或依赖，重跑红灯；删减使红灯消失就恢复该项。保留原始场景。偶发故障记录同条件下失败次数/总次数，修复后按相同条件比较。**进入 S3：**缩小后仍捕捉同一症状，剩余因素已逐项核对或标明未排除项。若发现红灯只是环境启动错误或另一缺陷，回 S1。

## S3 写出可证伪假设

复杂故障通常列 3–5 个相互竞争的原因，按证据和检验成本排序。每项写出「若为真会观察到什么、什么结果会推翻它」；明显单点错误可直接检验。**进入 S4：**至少一个实验能区分主要候选；预测说不清时回 S2 补观察。

## S4 核实根因

每次探针只检验一条预测并改变一个关键条件。优先断点或局部检查；临时日志放在分歧边界并标记唯一前缀。比较正常与失败输入、状态或版本，找到首次偏离。性能问题先测同环境基线，再用 profiler 或查询计划定位。能通过开关疑似条件让红灯随之变化时保留对照；否则用执行轨迹与不变量证明「触发条件 → 错误路径 → 症状或被违反的不变量」，并说明未排除的解释。**进入 S5：**证据支持原因且主要替代解释已排除；推翻假设回 S3，信号失效回 S1。

## S5 固定并修复

选择经过真实故障模式的测试接缝，先确认针对性检查在旧行为下为红，再实施最小修复，使**同一检查**转绿。若自动测试只能复述内部实现，保留固定的人工或集成复现并记录自动化缺口。公开 API 行为变化时用 `design-apis` 核对兼容影响；扩大访问、生产写入或高成本探针需相应授权。**进入 S6：**针对性检查或固定人工复现由红转绿；仍红则按新证据回 S3、S4 或留在 S5。

## S6 原场景回归

依次重跑原始未缩小场景、针对性回归、受影响的相邻检查；相邻检查应覆盖修复所改变边界的正常行为，并说明选择依据。区分本次引入、既有失败和环境阻塞；本次引入的失败修复后重验，必要的针对性或相邻检查受阻则保留 S6 待验证。搜索并移除临时日志前缀，只清理本次创建且不需保留的探针和夹具。**进入 S7 完整交付：**用户原始场景已复测、原症状消失，受影响检查通过。**进入 S7 有限交付：**原始场景因缺输入或环境无法复测，但替代复现或独立不变量检查由红转绿，受影响检查通过；说明两者与原场景的对应关系及未覆盖处。新失败按证据回 S3 或 S5。

## S7 交付

报告症状、根因证据、代码改动、实际运行命令和结果、未覆盖范围。完整交付才称「原问题已修复」；有限交付只称替代场景或独立行为得到修复，并写明用户原始场景仍未知。诊断输出以 `<REDACTED>` 替代秘密；获授权创建提交或 PR 时写明根因与验证证据。停在 S0–S6 时报告当前状态和缺失证据。
