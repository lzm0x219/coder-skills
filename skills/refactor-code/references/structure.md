# 模块、目录与依赖

S2 处理模块拆分、目录重设计或共享抽象，S4 用同一变化实例验收收益。

## 从维护摩擦推导职责

追踪真实或用户指定变化需要修改的位置与理解的约定：聚合共同变化的知识，分离独立变化的策略，按领域职责命名。

明确模块拥有的数据、不变量、资源及外部操作；每层隐藏有意义的决策。兼容入口可转发，新增内部层须有独立职责。依赖指向稳定契约；同级互相导入时核对双方所需知识，选择合并同一职责、移动共享规则或传入有界操作。

共享状态有单一所有者，通过实例/有界操作传递依赖，按兼容账保留身份、缓存与异常语义。目录随职责设计。

## 目录重设计

1. 从兼容账确认稳定入口、实现路径和直接路径消费者，列出内部模块与生成文件。
2. 给出目标树、目录/关键文件职责及允许的依赖方向。
3. 按依赖顺序移动实现、更新引用并保持承诺入口可用。
4. 从项目权威生成入口更新生成文件；路径核验按[制品观察](compatibility.md#公开库声明与制品)。
5. 依下方结构证据验收目标布局。

## 去重复与抽象

对照两个实现的兼容账及变化原因，只提取消费者证实相同的不变量；语义不同的相似实现分别维护。业务差异留在明确调用点，共享函数只接受当前消费者所需参数。

检查抽取是否移动验证、日志、I/O、回调的时机，保持单次与重复调用的副作用次数。可配置差异用明确参数或有界操作；多个独立职责仍分别归属。

## 结构证据

比较 S0 实例改动前后需理解/修改的位置，核对职责是否收敛；可用循环依赖解除、状态归属明确、规则单一实现或稳定消费入口佐证。文件数、行数和 index 层数仅作描述。

行为、用户指定布局与依赖方向分别验收。新增层未隐藏决策或职责仍未收敛 → S2；用户指定布局有取舍时说明成本，按约定目标验收。
