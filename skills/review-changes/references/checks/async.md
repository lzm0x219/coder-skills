# 时序与故障

时序反例必须给出实际能发生的事件序列及其依据，不能仅因出现 async/锁就推定竞态。

<a id="a1"></a>

## A1 完成与错误的归属

触发：启动任务、改动 await/return、并行聚合或后台执行方式。

必须确定谁负责观察任务完成和失败，外部“成功”何时返回；追踪返回之前未完成的必需写入及无人观察的错误。并行聚合须查一项失败时其他任务是否继续产生副作用。

完成：成功与失败各有可观察的终态，调用者的完成契约成立。明确授权的后台任务可以不等待，但其耐久性、失败归属和关机处理必须有来源；不能把所有未 await 的任务一律报成错误。

<a id="a2"></a>

## A2 交错与过期写入

触发：多个任务读写同一状态，或新请求启动后旧请求仍可写结果。

必须找出共享对象、检查/写入之间的可交错点及现有序列化或版本保护。构造两条任务序列，例如读旧值→另一任务写入→旧任务覆盖，或第二次请求先返回→第一次后返回；确认入口允许该序列。

完成：能说明保护覆盖全部写入点，或给出导致错误终态的可达交错。单线程不等于无异步交错；反过来，入口已串行且不可重入时不能假设并行执行。

<a id="a3"></a>

## A3 重试与未知完成状态

触发：重试次数/条件、超时、断连恢复或失败后重放变化。

必须区分执行前失败与副作用提交后响应丢失；追踪重试是否保持同一操作身份、哪些错误可重试、次数和总时限是否有界。对会计费、发信或写状态的路径，检查提交成功→响应超时→重试的序列。

完成：重复调用的副作用符合契约，未知完成状态不会被当成“未执行”；有证据的幂等或补偿可以排除反例。不能因为返回超时就断言原操作没有提交，也不能要求纯读取具有写入幂等键。

<a id="a4"></a>

## A4 取消、超时与后续工作

触发：取消信号、超时包装、离开页面/关闭服务或取消传播变化。

必须追踪取消是否传给实际执行者，未停止的任务还能写什么，调用者是否仍等待或释放所需资源；检查取消期间启动的新工作及取消错误的处理。核实契约到底要求停止执行，还是仅停止等待。

完成：取消/超时后的允许终态有来源和执行路径，迟到结果不会违反该终态。仅停止等待不必然是缺陷；若契约要求无后续写入，而内部任务继续写，必须保留这条反例。

<a id="a5"></a>

## A5 资源与失败窗口

触发：连接、文件、锁、订阅、计时器或临时资源的创建/转交/清理变化。

必须确定创建者与释放者；沿创建中途失败、使用失败、取消和正常退出分别追踪释放。转交所有权后查接收者是否承担清理；检查清理自身失败是否覆盖原错误或使锁/事务保持占用。

完成：每个受影响资源在各条可达终止路径有唯一有效释放责任，或允许持续占用的明确生命周期。不能仅见 finally 就判清理通过：资源在进入 try 前创建失败、部分创建成功等窗口仍须核验。
