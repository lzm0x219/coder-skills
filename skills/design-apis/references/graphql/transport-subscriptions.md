# GraphQL 传输、订阅与文件

GraphQL 核心规范未规定通用 HTTP/WebSocket/SSE 传输或文件上传协议。仅将选定的传输协议写入适用契约并固定版本；不能把服务器框架行为当成 GraphQL 规范。

**G24｜HTTP binding｜使用 GraphQL over HTTP 时。** 固定具体 draft/实现版本，约定 POST JSON、可选 GET 编码、Accept/Content-Type、operationName/variables/extensions、multipart/batch/persisted-document 扩展。GET 只能承载 query，不得通过 GET 执行 mutation；query string 的 URL 长度、日志暴露和缓存键要纳入选择。定义不支持 method/media type、parse/validation/coercion 错误和 execution result 的 HTTP status/body 映射；消费者必须按 GraphQL response body 判定执行错误，不能只看 2xx。跨站 cookie auth 时按[共享安全契约](../common/security.md)CS06 定义 CORS/CSRF、防护源和 cookie 策略。证据：GET query、GET mutation 拒绝且无 resolver 副作用、POST JSON、错误阶段的媒体类型和状态码、CSRF 负例。参考：[GraphQL over HTTP working draft](https://graphql.github.io/graphql-over-http/draft/)；其状态是工作草案，不是 GraphQL 核心规范。

**G35｜HTTP 缓存｜query 响应可被 browser/client/CDN 缓存时。** 定义可缓存的 operation/身份范围、operation document 与 variables 如何共同确定表示、哪些 headers 影响响应、缓存 freshness/validation 和 schema/业务更新失效方式。私有或授权结果不得因同一个 query/hash 被不同主体共享；实现共享缓存时按 RFC 9111 对 Authorization 的明示许可执行并覆盖租户身份。GET 方便缓存不等于安全可缓存；若变量/敏感参数进 URL 会泄露到日志/历史且超 URL 限制，使用 POST 或持久文档并给出回退。字段级 caching 不能绕开对象权限。证据：同一 operation 不同变量/用户/租户缓存隔离、query 更新后失效、匿名与认证请求、身份撤权后的响应。参考：GraphQL.org [Performance: GET requests for queries](https://graphql.org/learn/performance/#get-requests-for-queries)、[Serving over HTTP](https://graphql.org/learn/serving-over-http/)、HTTP [RFC 9111 §3.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5)。

**G25｜订阅操作｜schema 提供 subscription 时。** 每个 subscription operation 应映射到有界、可授权的事件源；定义事件 payload 代表快照还是增量、事件顺序/重复/丢失承诺、过滤、持久在线授权、取消时资源清理和慢消费者策略。GraphQL subscription 执行不会自动承诺持久消息、重放或 exactly-once；如需断线续接，定义 cursor、保留窗口和 gap 检测并借助明确传输/broker 契约。重新连接必须重新认证/授权，过期 cursor 返回可恢复错误并给全量重同步路径。证据：正常事件、重复/乱序、断线重连、权限撤销、取消、慢消费者与过期 cursor。依据：GraphQL 规范 [Subscription](https://spec.graphql.org/September2025/#sec-Subscription)、[Subscribe and Map](https://spec.graphql.org/September2025/#sec-Subscribe-and-Map)、GraphQL.org [Subscriptions](https://graphql.org/learn/subscriptions/)；投递保证须由所用传输/消息系统另行规范。

**G26｜增量响应｜采用 `@defer`/`@stream` 或 multipart incremental delivery 时。** 指明客户端/服务端采用的具体实验性协议版本与媒体类型；规定初始 payload、后续 patch 路径/标签、完成信号、错误对应 patch、取消和部分流中断恢复。不能把尚未标准化的 draft 当作 core GraphQL response；消费者需识别不支持/中断并执行完整 query 回退或重新获取。证据：初始结果、多个 patch、patch 错误、提前 EOF、取消、客户端不支持协商回退。参考：Apollo [incremental delivery v0.2](https://specs.apollo.dev/incremental/v0.2/)；版本处于实验/草案能力，部署前核实目标实现。

**G27｜文件传输｜mutation 接收/返回文件时。** GraphQL 没有核心文件 scalar 或 multipart upload 标准。优先把二进制放入独立 HTTP upload/download 资源，然后用 GraphQL mutation 创建/完成/关联该资源；若选社区 multipart upload 协议，锁定其规范和执行器版本，限定大小/类型/数量，指定签名/鉴权、重复文件、流清理、失败清理与 URL 过期规则。下载 URL 的授权、缓存和 Range 行为归对应 HTTP contract。证据：截断、重复文件、声明类型与真实内容不符、取消后临时文件清理、过期 URL 与跨租户访问。依据：GraphQL.org [File Uploads](https://graphql.org/learn/file-uploads/)；这是推荐的传输分层，不是核心 GraphQL MUST。
