# Event identity, payload and schema evolution

本页扩充 [E01–E04、E08](../events.md)。CloudEvents 是可选事件 envelope；JSON Schema / Avro / Protobuf 等负责 payload encoding/schema；AsyncAPI 描述应用消息接口。分别注明使用版本与 profile。通用 field semantics、sensitivity 与兼容性门槛由 [shared data](../common/data.md) / [shared evolution](../common/evolution.md) 定义；本页只补消息封装和 producer-reader 矩阵。

## 规则

| ID | 适用条件与强度 | 可执行动作、失败处理和证据 | 来源 |
|---|---|---|---|
| ES01 | 所有领域事件。**Skill MUST** | 逐字段区分事件事实（past-tense、不可变）、command/request（要求未来动作）与 snapshot/read model。记录 producer、业务触发的提交点、产生时间和业务发生时间、aggregate identity/version、data 是完整快照还是差量。发出时点无法和业务写入同事务时，列出遗漏/重复窗口、补偿源和 reconciliation。 | [CloudEvents Core §1–2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md#abstract)只提供 envelope/event 语义；事务 outbox 是应用模式。 |
| ES02 | 使用 CloudEvents。**协议等级与 Skill 要求分别应用** | 固定 `specversion` 与 format mode。CloudEvents producer(s) MUST 确保每个不同事件的 `source + id` 唯一；多个 producer 共用同一 source 时须协作确保唯一性，不能把该责任当作 envelope 自动提供的保证；重送 MAY 复用 `id`，本 Skill 的稳定事件身份合同须决定并与 delivery/attempt 区分。`time` 可选，出现时按事件发生时间规则处理；未知发生时间按规范允许的替代策略保持一致，不把可选属性变必填。`dataschema` OPTIONAL，出现时 MUST 是非空 URI；不兼容 schema 改动 SHOULD 用不同 URI。URI 可取得、保留与版本发布是本 Skill 的消费设计要求，另记录是否更换 `type`，不能误称 CloudEvents 协议强制。 | [CloudEvents Core v1.0.2 §3](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md#context-attributes)、[JSON format §3](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/formats/json-format.md) |
| ES03 | structured/binary 分别编码，或任何签名/哈希依赖 wire bytes。**Skill MUST** | 对每种实际 wire mode 列出 context attributes、headers、content type、payload bytes 和 schema validator。先保留原始 bytes 做签名/校验，再 decode；重新序列化只作为新消息构造步骤。缺失/错误 content type、重复 envelope 属性、非法编码必须定义拒绝或隔离行为。 | [CloudEvents JSON Event Format](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/formats/json-format.md) |
| ES04 | 新增/修改已发布 payload schema。**Skill MUST** | 固定 encoding/schema draft、serializer/parser 版本、实际 old/new reader-writer 对。对所有 active consumer/writer 跑 old writer→new reader、new writer→old reader；注册中心的 backward/forward/full/transitive 需映射到实际支持窗口。字段/枚举/null/default/unknown property 的通用兼容定义走 shared evolution；格式 validator/registry pass 不替代 wire fixture 和运行版本校验。失败时采用新 `dataschema`/type 或明确 migration/dual-read rollout。 | [CloudEvents dataschema](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md#context-attributes)、[JSON Schema 2020-12](https://json-schema.org/draft/2020-12/json-schema-core)、[Confluent compatibility modes](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)；registry 行为是具体产品配置。 |
| ES05 | 消费者需要处理未来字段/type。**Skill MUST** | 显式选择 strict/lenient reader 并验证真实 consumer library。Lenient unknown field/enum 要进入可观测的 safe fallback，不能变更权限或副作用；strict consumer 需要 staged rollout。对 JSON Schema 2020-12 composition 检查 `unevaluatedProperties` 与 subschema annotation 的实际效应。 | [JSON Schema object reference](https://json-schema.org/understanding-json-schema/reference/object)、[Core §10.3](https://json-schema.org/draft/2020-12/json-schema-core) |
| ES06 | 注册中心控制 schema 发布。**Skill MUST** | 记录 registry vendor/version、subject naming、compatibility mode、transitive flag、override/subject scope、serializer/deserializer 与 rollout policy；提交受支持历史版本集合的 register/check 结果。registry API 只证明它配置的兼容算法，不证明 payload business meaning、所有非 registry consumer 或历史清理安全。 | [Confluent schema evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)仅适用于 Confluent profile。 |
| ES07 | 多 tenant / 多主体共用 broker。**Skill MUST** | 复用 [shared security](../common/security.md) 的身份/tenant gate；在目标 broker ACL 中逐 principal 展开 producer publish、consumer subscribe/fetch、schema registry read/write、DLQ read/write/admin。拒绝 payload 自报 tenant 跨权；credential rotate/revoke 生效窗口按实际 broker/provider profile 证明。 | 依协议引用 [Kafka ACL](https://kafka.apache.org/42/security/authorization-and-acls/) 或 [NATS subject authorization](https://docs.nats.io/learn/security/authorization)；ACL 是部署 profile。 |
| ES08 | 事件可能包含个人/秘密/高基数字段或可跨境数据。**Skill MUST** | data minimization 表列目的、消费者、敏感级别、静态/传输保护、日志脱敏、retention/delete/copy/backup 期限和 replay policy。不能证明消费者/registry/DLQ 的 erase 路径时，标记保留风险与阻塞决策。 | 组织/法规 profile；CloudEvents 与 AsyncAPI 不定义业务数据生命周期。 |
| ES09 | CloudEvents 经中介转发或消费者接受事件。**协议 MUST / SHOULD + Skill** | 大小按实际 wire-size 计，包含所选 format/binding 的协议帧元数据、事件元数据和 data，不能只量 payload JSON；跨协议/重编码 SHOULD 考虑最不高效的协议与编码。中介 MUST 转发大小不超过 **64 KByte** 的事件；消费者 SHOULD 接受至少该大小，偏离需说明约束及影响。记录 broker/client 实际上限与压缩前后预算；64 KByte 是互操作基线，不是所有 API/提供方统一最大值。 | [CloudEvents v1.0.2 Size Limits](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md#size-limits)；证据用完整 wire 的边界/超界消费或中介样例，生产限制另验。 |

| ES10 | 使用 CloudEvents context / extensions。**协议 MUST / SHOULD + Skill** | 验证 required `specversion/id/source/type`；v1.0.2 的 `specversion` 值 MUST 为 `1.0`，`id/type` 是非空 String，`source` 是非空 URI-reference（绝对 URI RECOMMENDED）。属性名 MUST 只含小写 ASCII 字母或数字；长度 ≤20 是 SHOULD，不是 MUST。context 与 extension 值 MUST 遵循类型系统：Integer 为 signed 32-bit，String 不得含 U+0000–001F、U+007F–009F、Unicode noncharacters 或 unpaired surrogates；URI、URI-reference、Timestamp 按各自格式验证。extension definition SHOULD 完整定义名称、类型、语义含义和可能值/值域；可选性及业务限制另列为 Skill/应用要求。消费者不支持可选属性时静默忽略，producer 须准备其被忽略的情况；中介 SHOULD 转发可选属性。不能据 extension 自报值授权。额外必填项或更严格字符/长度限制标为应用 profile。提交缺必填、空值、整数边界与越界、非法字符串的拒绝证据；schema 无法覆盖的解析责任单列。 | [CloudEvents Core v1.0.2：Attribute Naming、Type System、Required Context Attributes、Extension Context Attributes](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md#context-attributes)；未知属性见 Notations and Terminology。 |
| ES11 | 使用 CloudEvents JSON Event Format。**协议 MUST / MAY + Skill** | 固定 context 类型到 JSON 的映射；可选属性 MAY 编为 `null`，解码 MUST 等价于 unset/omitted（不把 `data:null` 当缺席）。二进制 data MUST 使用 base64 String 的 `data_base64`；它与 `data` 互斥。JSON data MUST 是实际 JSON value，不能把 JSON document 再编码成 String；原值是 JSON String 时 MUST NOT 再 parse 一次。采用非 JSON data 时按 content type 声明 String 表示/解码；缺 datacontenttype 时按 JSON format 的 SHOULD 处理并记录 profile。extension 的可选 secondary JSON mapping 必须有相应 extension 定义，并保留要求的 primary mapping；定义 secondary mapping（及其修订）时 MUST 为当时 CloudEvents core 中其他 event format 定义显式映射。核对 extension 定义的格式清单与每种映射，缺项时补定义或不采用该 secondary mapping；不能泛称所有对象映射都违规。提交两种 data 同时出现、base64 错误、double encoding、可选 null→unset、JSON String 不二次解析的消费/拒绝证据；仅 JSON Schema pass 不证明原始数值词法、解码或 serializer 行为。 | [JSON Event Format v1.0.2 §2.2、§3（Envelope）、§3.1.1–3.1.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/formats/json-format.md)；Integer 的 JSON 数值词法不允许小数或指数形式，按 §2.2（Type System Mapping）检查原始 token。 |

## 验收边界

至少提供正式 schema、合法/拒绝的 wire samples、旧 producer/consumer 矩阵、registry profile 与跨租户访问矩阵。schema-validator pass 不是注册中心测试；注册中心 pass 不是所有 reader 的兼容证明。没有真实版本化消费者时，兼容项标为“设计案例”，不能写运行已证。
