# Library / SDK API 评审

适用：设计提案、公共接口变更或发布评审。先读取与任务相关的基础、命名、运行、远程及演化规则，再用本文件检查歧义、取舍和交付证据。

## V. API 评审

**V01｜通用｜MUST 在实现冻结前评审公共契约。** 提案包含用例、调用示例、类型/错误/寿命、兼容矩阵及替代方案；代码评审再核实实现符合契约。例外/评审：微小内部 API 可走简化流程；评审能否指出调用者会如何误用？

**V02｜通用｜MUST 记录例外与发布结论。** 偏离 `SHOULD` 要记理由、风险与接受者；无法验证的兼容维度标记未知，不得写作通过。例外/评审：无偏离无需记录；审批人知道哪些事实已测、哪些是推断吗？

依据：[.NET Framework Design Guidelines](https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/)、[Kotlin Library Authors’ Guidelines](https://kotlinlang.org/docs/api-guidelines-introduction.html)。

## 设计 smells 与处理

下表是审查线索，不是自动拒绝条件。每项给出症状、危害、可接受情形与典型修复；触发时仍需看真实调用代码。

| Smell | 症状与危害 | 何时可接受；典型修复 |
| --- | --- | --- |
| Boolean blindness | 多个 `true/false` 在调用点不可辨；交换后仍可编译。 | 布尔就是领域事实时可用；改为命名选项或独立操作。 |
| Primitive obsession / stringly typed | 多个 ID、金额、单位全用字符串/数字；混传难发现。 | 局部低风险脚本可用；引入有校验的语义类型。 |
| God object / god method | 单对象或方法承担多个不相关流程；难学、难演化。 | 领域事务本身不可拆时可保留；拆成正交操作。 |
| `Manager`/`Helper`/`Util` 膨胀 | 名称不表示职责，新功能无脑归入；概念边界消失。 | 确属领域术语可保留；按调用者概念重新命名和分组。 |
| 可选参数过多 / 伸缩构造器 | 同一函数含大量默认值、互斥组合或多层构造；调用难读。 | 少量稳定参数可用；采用配置对象、构建器或工厂。 |
| 重载 / 方法组合爆炸 | 同一操作出现很多参数排列和变体；推断歧义、维护困难。 | 少数清晰重载可用；归并成明确选项。 |
| Null ambiguity / sentinel / magic value | `null`、`-1`、空串同时代表多种结果；错误处理靠猜。 | 只有单一稳定含义时可用；显式建模结果状态。 |
| 隐式全局状态 | 配置、时钟、当前客户端在全局变化；测试互相污染。 | 固定进程级配置可用；通过显式上下文或构造注入。 |
| 隐藏 I/O / 隐藏变异 | 读属性或普通 getter 触发远程请求/修改；性能与副作用意外。 | 惰性机制有清楚约定时可用；在名称、类型或文档暴露。 |
| 依赖泄漏 / 抽象泄漏 | 公共签名暴露内部框架或存储类型；升级被外部绑定。 | 生态互操作收益显著时可用；稳定边界层或独立低层入口。 |
| 过宽接口 / 脆弱基类 | 扩展者必须实现无关方法，基类更改破坏子类。 | 完整事务能力不可拆时可用；小接口、组合、受限扩展。 |
| 过早抽象 / 猜测式扩展 | 没有调用案例却预设插件与继承点；未来受兼容承诺束缚。 | 明确平台产品目标时可提前建模；先用最小稳定原语。 |
| 意外公共 API / 扩展点 | 默认导出实现类或可覆盖方法；用户开始依赖。 | 刻意公开且测试/文档完整时可用；收紧可见性。 |
| 时间耦合 / 无效中间态 | 必须按隐秘顺序调用，错误只能运行时出现。 | 资源流程天然分阶段时可用；用状态对象或明确迁移。 |
| 弱错误类型 | 所有故障同一异常/字符串；调用方无法决策。 | 极小无恢复分支 API 可用；稳定类别与上下文分开。 |
| 无意义 getter/setter | 仅为暴露内部字段而加访问器；强绑定表示与可变性。 | 领域属性真实稳定时可用；公开行为或值对象。 |
| 配置对象垃圾桶 | 无关设置塞进单个 `Options`；冲突和默认值难懂。 | 少量紧密相关选项可用；按生命周期/能力拆分。 |

## 原则冲突与默认选择

| 冲突 | 两侧收益与成本 | 默认选择；何时反转 |
| --- | --- | --- |
| 便捷 vs 最小表面 | 便捷降低上手成本，但每个方法增加永久维护面。 | 先提供可组合原语；高频任务经调用样例证明后加少量便捷入口。 |
| 灵活 vs 简单 | 配置覆盖更多场景，但让普通路径难懂。 | 常用路径少选项；有真实差异且默认不安全时显式配置。 |
| 强类型 vs 样板 | 类型防误传，但包装层增多。 | 优先为高风险值建模；局部低风险值维持原生类型。 |
| 显式 vs 冗长 | 显式利于审查，但调用可能繁琐。 | 让风险、单位、所有权显式；无歧义惯例用短形态。 |
| 不可变 vs 性能 | 不可变减少别名问题，复制可能昂贵。 | 默认值对象不可变；高吞吐路径提供受控可变视图并写清寿命。 |
| 抽象隔离 vs 生态互操作 | 隔离便于替换依赖，但可能丢失原生能力。 | 公共概念独立；在生态类型确为事实标准时提供明确适配或低层入口。 |
| 稳定 vs 改进 | 兼容保护用户，旧缺陷长期存在。 | 兼容新增与弃用迁移；安全/正确性严重问题走明确破坏性发布。 |
| 可扩展 vs 可演化 | 用户扩展方便，库难新增成员或改变调用顺序。 | 先组合/回调；需要用户实现且能定义契约时开放扩展点。 |

## API 评审流程

1. **Proposal：** 说明目标调用者、真实任务、备选方案与暂不支持的场景。
2. **Concept model：** 先用中性称谓确认公开对象的 ID、生命周期、状态、结果和相互关系；区分既有事实、已定决策和待验证假设。关键关系未知时按[命名准入](naming.md)留下未决结论；仅缺既有用语时可以记录正式命名取舍。
3. **Call site：** 根据概念模型写普通与失败调用；生命周期、并发或边界行为影响使用时再展示对应调用。让未参与实现的人试用。
4. **Contract：** 审核导出、签名、类型、错误、资源、线程、成本和安全边界。
5. **Evolution：** 固定稳定性级别，检查旧消费者及扩展者；写出未来增加选项/状态的路径。
6. **Documentation：** 写语义文档、最小迁移示例与发布说明草稿，借此发现含糊设计。
7. **Verification：** 对争议名称走查相反解释和信息不足的案例；对命中的异步、资源和失败分支检查同时发生的错误及优先级。目标语言已定的具体提案按[设计期交付](deliverables.md)检查候选公开声明与消费者调用；变更已发布接口时用旧消费者静态检查候选声明。实现或发布候选包存在后，再运行示例与旧消费者。
8. **Decision：** 记录批准人、偏离规则的理由、未验证风险与发布级别。

API 评审先决定调用者能依赖什么，代码评审再判断实现是否兑现；只在实现后做普通 code review，通常来不及改变已扩散的公共签名。

## 可复制的 API Proposal / PR 清单

```markdown
### 目的与调用点
- [ ] 目标调用者、普通/边界/失败场景明确；确需新增公共入口
- [ ] 示例从真实导入方式开始，调用点无需实现细节也能读懂
- [ ] 常见任务简洁，复杂任务可通过正交能力完成
- [ ] 具体语言级提案有独立候选公开声明和可检查的消费者文件；只输出概念稿时明确未作语言级验证

### 公共表面与模型
- [ ] 导出清单、稳定/实验/内部边界明确；无意外再导出
- [ ] 公开对象、执行句柄与结果先用中性称谓建模；既有事实、已定决策和待验证假设有来源
- [ ] 易混名称经过相反解释及信息不足走查；已确认依据不足时，记录正式设计取舍或标为暂定/未决
- [ ] 公开词汇表和完整调用点已核对；同一概念同名、不同概念异名
- [ ] 方法动词、完成阶段与返回形态相符；类型名表示调用者持有的对象
- [ ] 参数顺序、单位、缺省、空值/缺失/未知语义明确
- [ ] 可选项、布尔值和重载无歧义或组合爆炸

### 运行契约
- [ ] 成功、失败、部分成功和副作用可测试
- [ ] 错误类别可程序化处理；错误上下文不含秘密
- [ ] 资源所有权、关闭、重复关闭和失败清理明确（如适用）
- [ ] 多个资源都尝试关闭；主操作与清理同时失败时，调用方能取得各项错误或明确的优先级（如适用）
- [ ] 异步完成、取消、超时、并发、回调顺序明确（如适用）
- [ ] 请求发出前的取消与凭据/配置获取失败同时发生时，错误归类明确（如适用）
- [ ] 凭据获取是否计入尝试、重试及整体等待预算明确；提供者不响应取消时 SDK 何时停止等待（如适用）
- [ ] 主要 I/O、分配、分页/流式和成本边界可发现（如适用）
- [ ] 危险/付费/高权限操作不依赖隐式默认值

### 远程 SDK（如适用）
- [ ] 客户端配置来源及优先级、凭据刷新/轮换的生效时机明确
- [ ] 重试条件、总尝试次数、等待与超时预算、幂等键复用及未知结果明确
- [ ] 分页继续令牌、批量部分成功、流释放和响应元数据访问明确
- [ ] 长任务状态/结果、停止本地等待与取消远端任务的语义分别明确
- [ ] SDK 与服务版本的支持范围、默认值和预览能力边界明确

### 演化与交付
- [ ] 继承、接口或插件扩展点确有场景且契约可演化（如适用）
- [ ] 源码、ABI、行为、数据和环境兼容矩阵按承诺填写
- [ ] 变更已发布接口时，设计期用旧消费者检查候选声明的源码兼容；实现或发布候选包存在时再运行旧消费者，未运行的行为维度标为未验证
- [ ] 弃用给出替代、迁移、期限；发布级别符合版本政策
- [ ] 发布时，包导出、类型声明、示例和文档同版本
- [ ] 偏离规则、未知风险、批准人和验收证据已记录
- [ ] 分别报告声明/调用静态检查、语义走查与运行验证；未运行的不写作通过
```

## 最值得记住的 20 条

1. 先确认公开对象，再写调用代码与公共签名。
2. 公开入口必须有明确稳定性级别。
3. 只公开调用者需要依赖的概念。
4. 一个领域概念使用一个稳定名称。
5. 相同原始类型易混淆时加入语义区分。
6. 不要让调用者构造无效中间状态。
7. 参数和默认值要在调用点可理解。
8. 缺失、失败、未知与未加载不能混用。
9. 错误分类要可程序化处理。
10. 失败后副作用与状态必须可判断。
11. 资源归属、关闭与借用寿命必须明确。
12. 显著 I/O 和成本不能隐藏在廉价外观下。
13. 取消、超时和并发是公共契约。
14. 优先少量正交原语，再加证实有用的便捷入口。
15. 扩展点只为真实场景开放，并写清其长期契约。
16. 不要无意导出第三方依赖和实现类型。
17. 文档写不清时先检查 API 设计。
18. 兼容性分源码、ABI、行为、数据和环境核验。
19. 弃用必须有可执行迁移路径。
20. 变更已发布接口时，设计期检查旧消费者，发布前再用真实候选包验收。
