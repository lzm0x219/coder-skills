# 框架、插件与第三方扩展点

适用：调用方将实现接口/trait/protocol、继承公开基类、注册插件/中间件、覆写钩子或接收框架回调。把第三方实现者视为独立消费者，并评估“新增能力”对既有实现者的影响。

## L. 继承与扩展点

L01–L03 从基础契约迁入本页，规则 ID、等级、措辞与依据保持不变。当前追踪使用 `library-sdk/extensions:L01` 等文件范围；历史 `library-sdk/design:L01` 仍对应历史源版本。

**L01｜条件｜SHOULD 只为明确的第三方扩展场景开放继承或实现。** 说明哪些方法可覆盖、何时调用、必须维持的不变量；否则以组合或受限扩展替代。例外/评审：框架核心就是用户子类化时需要公开；新增基类方法会破坏旧子类吗？

**L02｜条件｜MUST 为公开扩展点定义版本化契约。** 接口、trait、protocol、插件和钩子要说明生命周期、错误、线程、顺序及新成员策略。例外/评审：实验扩展点可承诺较弱稳定性但必须标注；未来加能力是否要求所有实现者修改？

**L03｜条件｜SHOULD 避免脆弱基类与过宽接口。** 将独立能力拆成小接口；默认实现不得偷偷依赖子类未文档化行为。例外/评审：广接口有不可分领域事务时可保留；一个消费者是否只需实现极少成员？

依据：[.NET Extensibility](https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/designing-for-extensibility)、[C++ Core Guidelines Classes](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)、[Rust Cargo SemVer](https://doc.rust-lang.org/cargo/reference/semver.html)。

## Z. 扩展者契约

**Z01｜条件｜MUST 说明扩展点的所有可观察调用时序。** 定义注册/启用、初始化、调用、失败、停用与卸载顺序；多实现者时定义先后、短路、组合及同优先级处理。回调能否同步重入注册方、嵌套调用或在取消后迟到也须明确。若无稳定顺序保证，应明确消费者不能依赖顺序。证据为旧扩展者消费者与顺序反例。来源参考：.NET Framework Design Guidelines「Events」及「Virtual Members」要求审慎设计覆盖点；具体顺序条款为综合设计建议。

**Z02｜条件｜MUST 定义线程、并发及回调上下文。** 指明框架是否串行调用同一扩展实例、不同实例是否并发、回调线程/执行器、线程亲和资源及调用者是否可阻塞；异步钩子说明并发度、取消/超时传播和重入。不能仅依赖“线程安全”标签替代对象级保证。证据为并发调用消费者或静态线程契约检查。来源：Rustonomicon FFI 异步回调的跨线程安全边界、目标框架的官方插件/回调 API 文档；跨框架综合要求。

**Z03｜条件｜MUST 将扩展者失败映射成有界框架行为。** 对异常、拒绝、超时、取消、部分结果和致命失败分别写明传播、隔离、重试及后续钩子是否继续；错误中包含哪个扩展者身份，敏感信息如何清除。框架不得默默吞错或无界重复调用。证据为一个失败插件加后续插件的调用记录/契约消费者。来源：.NET Virtual Members 建议避免虚成员带来异常复杂性；本条为综合要求。

**Z04｜条件｜MUST 设计扩展接口的加法演化。** 对第三方可实现的 interface/trait/protocol，新增必需成员通常会要求已编译/已发布实现者更新；优先初始拆成小能力接口、提供独立适配器/可选能力、或按目标语言官方兼容机制演进。默认实现只有在不改变既有语义且可安全调用时采用。旧实现者消费者必须参与源码/二进制兼容检查；不得把“新增成员”笼统判为兼容。来源事实：.NET Interface Design 建议避免公开可扩展接口、优先抽象类（含版本化理由）；Java JLS §13 与 Kotlin Backward Compatibility 指南分别定义语言特定二进制/源兼容限制；具体机制必须按目标语言核验。

**Z05｜条件｜MUST 显式处理可选能力协商。** 插件版本、运行时 feature 或宿主能力并非所有实现都支持时，使用能力查询、版本化子接口或注册时握手；写出缺失能力时是拒绝注册、降级还是禁用相关操作，并为未知能力/未来值规定策略。不要通过试调用后捕获任意异常来猜能力。证据为支持/不支持/未知三类扩展者消费者。此为框架综合设计要求，无跨语言统一协商标准。

**Z06｜条件｜MUST 为插件卸载设定静默屏障。** 明确停止新调用、取消/等待在途任务、撤销事件订阅、释放宿主资源和卸载代码的先后关系；何时可卸载动态库、回收插件状态或断开上下文必须可判定。卸载 API 若超时或失败，返回仍在使用的资源/回调信息，不伪称完成。证据为卸载期间迟到回调与在途任务反例。来源参考 Rustonomicon FFI「Asynchronous callbacks」关于销毁后禁止回调；其回调规则不是通用插件卸载规范，本条是谨慎外推。

**Z07｜条件｜SHOULD 使扩展接口窄且不泄漏私有实现。** 每个实现者只承担同一能力的必要职责；用组合能力、默认适配器或注册选项避免为了扩展一个钩子而实现无关方法。给上下文传稳定抽象类型，不把内部线程池、存储对象或传输客户端作为永久插件 ABI，除非它们本身就是承诺的扩展面。来源事实：.NET Interface Design、Virtual Members；C++ Core Guidelines C.35/C.137 等设计建议；不是强制标准。

**Z08｜条件｜SHOULD 为每类扩展面标明稳定级别与兼容策略。** 区分稳定、实验、宿主专用与内部钩子；说明版本范围、最低宿主版本、弃用通知与适配器迁移。低稳定级别不能免除对崩溃/资源泄漏等运行安全的定义。证据为扩展者兼容矩阵与迁移消费者。来源：Kotlin Library Authors Backward Compatibility、Cargo SemVer Compatibility；本条按项目版本政策综合。

## 评估消费者

以一个来自旧版本的扩展实现者编译/加载候选框架；分别覆盖成功调用、扩展拒绝、并发/重入及卸载。如果没有真实旧实现或候选运行时，提供可编译的最小实现者 fixture，并将运行/ABI 兼容标为未验证。框架自身的单元测试不能替代第三方实现者兼容证据。
