# Library / SDK 兼容与演化

适用：修改已发布接口、运行环境或包产物时。先固定旧版消费者与稳定性承诺，再评估每个兼容维度。

## S. 兼容性

**S01｜通用｜MUST 按项目承诺分别评估源码、二进制/ABI、行为和语义兼容。** 源码兼容指旧消费者仍编译/类型检查；二进制指旧产物仍加载/链接；行为/语义指旧调用仍得到承诺含义。例外/评审：纯脚本库通常无需 ABI；项目到底承诺哪些维度？

**S02｜条件｜MUST 检查公开可穷举集合与扩展点的新增成本。** 新枚举成员、重载、默认方法、接口成员或公开字段，即使“只新增”，也可能导致穷举失败、解析歧义或下游实现失败。例外/评审：项目可声明集合开放并要求未知值处理；旧消费者对新增项如何反应？

**S03｜条件｜MUST 审核序列化和持久化形式。** 当公开类型可持久化、跨进程、或作为缓存键时，字段名、默认值、格式及解码旧数据的能力属于独立兼容维度。例外/评审：对象明确禁止序列化时不适用；旧数据在新版本能否读取？

**S04｜通用｜MUST 记录支持环境的兼容范围。** 最低语言/运行时、操作系统、架构、依赖版本及包导出形式变动可能破坏用户，即使签名不变。例外/评审：仅受控单环境内部库可缩小矩阵；旧部署还能安装和运行吗？

依据：[Go 1 Compatibility](https://go.dev/doc/go1compat)、[Cargo SemVer Compatibility](https://doc.rust-lang.org/cargo/reference/semver.html)、[Kotlin Backward Compatibility](https://kotlinlang.org/docs/api-guidelines-backward-compatibility.html)。

## T. 版本与演化

**T01｜通用｜SHOULD 优先做兼容的加法演化。** 新入口、旧入口转接、默认行为保持；若新旧语义不同，用新名字或显式版本边界。例外/评审：严重安全或正确性问题可能要求破坏性修复；旧调用是否仍有同义行为？

**T02｜通用｜MUST 为弃用提供替代与迁移路径。** 指明替代入口、迁移示例、告警方式、最早移除时点及对应发布政策。例外/评审：紧急安全移除可加速但要解释影响；调用者能否机械迁移？

**T03｜条件｜MUST 按项目已声明的版本政策选发布级别。** 若采用 SemVer，先定义公共 API，再依据真实兼容性选择 MAJOR/MINOR/PATCH；`0.x` 默认不稳定，但项目可承诺更强兼容。例外/评审：非 SemVer 项目遵守自己的政策；版本号是否准确传达破坏性？

**T04｜通用｜MUST 核对发布产物与文档一致。** 导出清单、声明文件、二进制、示例、变更说明和版本标签须对应同一候选包。例外/评审：纯源码库也要验实际安装包；用户安装后能导入文档中的名字吗？

依据：[Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html)、[Cargo SemVer Compatibility](https://doc.rust-lang.org/cargo/reference/semver.html)、[TypeScript Publishing](https://www.typescriptlang.org/docs/handbook/declaration-files/publishing.html)。

## API 演化与兼容工程

兼容性应按**消费者类型 × 维度 × 发布阶段**判定。源代码、编译后的二进制、类型声明、序列化数据、运行行为和可用环境可能分别失败；不能用“旧符号还在”概括。Go 的 Go 1 承诺主要是源码级，[官方兼容说明](https://go.dev/doc/go1compat)明确不保证跨版本编译包的二进制兼容。Rust [Cargo 指南](https://doc.rust-lang.org/cargo/reference/semver.html)也把“新增公开项可能产生罕见歧义”列为风险，说明加法不是数学上的绝对安全。

| 维度 | 判断方法 | 典型破坏 |
| --- | --- | --- |
| 源码/类型 | 设计期用旧消费者检查候选公开声明；候选包存在后再对真实包编译或类型检查。两次结果分别记录。 | 改名、参数、泛型约束、可空性；新增重载造成歧义。 |
| 二进制/ABI | 在承诺的目标运行时加载、链接旧二进制。 | 布局、符号、虚表、调用约定变化。仅适用有此承诺的生态。 |
| 行为/语义 | 运行正常、失败及边界样例，比较承诺语义。 | 默认值、错误分类、排序、副作用、重试和线程语义变化。 |
| 数据/持久化 | 用旧版本样例数据读写新版本。 | 字段、枚举、编码或缓存键改变。仅适用公开持久化格式。 |
| 环境/包 | 从真实安装包导入并在支持矩阵运行。 | 最低运行时提高、模块路径变更、依赖冲突、声明文件错位。 |

**变更流程。** 设计期：① 固定旧版公共表面与代表性消费者；② 写“旧调用 → 新调用”的差异表；③ 判断能否用转接层保留旧语义；④ 对破坏项给迁移示例与弃用窗口；⑤ 用旧消费者静态检查候选声明，按项目政策拟定发布级别。实现/发布候选包出现后：⑥ 构建候选包并运行旧消费者，核对行为、数据和环境；⑦ 用候选包更新示例与发布说明。设计期无法验证的维度标为未知，不提前写作通过。

示例：把 `open(path, timeout?)` 改成 `open(options)` 会破坏旧源码；保留旧入口并委托新入口是兼容方案。若把默认超时从 `30s` 改为“无限”，即便签名未变也可能改变调用方的故障恢复，须做行为兼容评审。向一个允许调用方穷举的结果类型添加 `Pending` 也可能破坏旧匹配逻辑，应在最初就决定其开放/封闭边界。

**弃用最小记录：** 旧入口、替代入口、行为差异、迁移代码、告警方式、开始与最早移除版本、受影响消费者。若采用 [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html)，公共 API 必须先被清楚定义；兼容功能用 MINOR，不兼容改动用 MAJOR，兼容修复用 PATCH。版本号不能替代迁移，也不能自动证明行为兼容。
