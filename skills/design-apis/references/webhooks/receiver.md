# Webhook receiver contract

本页扩充 [WH01–WH04、WH08、WH11](../webhooks.md)，用于接收任意 provider callback。Provider-specific headers/status/timeout 以 [profiles.md](profiles.md) 为准。认证凭据、对象授权和通用资源保护引用 [shared security](../common/security.md)。

| ID | 条件、强度 | 具体规则、失败/恢复和证据 | 来源 |
|---|---|---|---|
| WR01 | 所有 receiver。**Skill MUST** | 接收 pipeline 明确 byte cap→签名/身份验证→parse/schema validate→durable inbox enqueue→ACK→异步副作用。每一阶段分类 2xx/4xx/5xx 或 provider 约定；unauthenticated 请求不产生业务副作用。队列不可用/DB commit 失败时只有已可靠接收才 ACK，否则返回明确 retry signal。 | GitHub 要求快速 2xx 并建议 queue：[best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)；固定 profile 可不同。 |
| WR02 | 请求签名原始 body。**Profile MUST** | HTTP server 在 JSON/form 解码、字符集变换、空白规范化、proxy body mutation 之前留存受限大小的原始 bytes；用 profile 的精确 signing input 计算 MAC/签名，并对等长二进制比较常数时间验证。超限先拒绝且不得完整落盘/日志。只有通过认证后才解析和校验 content-type/schema。 | [GitHub validation](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)、[Stripe signature](https://docs.stripe.com/webhooks/signature)。 |
| WR03 | provider header/body 中事件类型或 action 未知。**Skill MUST** | 先确认签名覆盖哪些身份头；若只签 body，把未签 header 当未可信 routing hint，不能用它单独执行敏感动作。未识别 type/action/schema version 不触发 handler；把已认证 payload 持久保存到隔离/parking，ACK or retry 依 profile 和升级 SLA 决定，并报警。 | [GitHub best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)；profile signature doc。 |
| WR04 | 重复 delivery 与业务副作用。**Skill MUST** | 用经过认证且稳定的 event identity 建 inbox unique key；若 provider delivery id 只识别 attempt redelivery，另用业务 event ID / aggregate version。并发重复的 claim、business effect、completion checkpoint 必须在同一 DB transaction 或可靠状态机中原子；若 side effect 外部系统，传同一 idempotency key 或提供 reconciliation。 | 数据库事务/外部 API profile；模型用例不能宣称 atomic/exactly-once。 |
| WR05 | 签名含时间戳/nonce。**Skill MUST** | 同时检查 timestamp freshness 和已处理 stable ID；timestamp 只是限制捕获请求重放的时间窗，不代替持久幂等。定义允许 clock skew、source of time、未来/过去 boundary、provider 每次重投 timestamp 是否刷新、clock drift 监控及 skew 故障恢复。 | Standard Webhooks profile：[spec](https://github.com/standard-webhooks/standard-webhooks/blob/v1.0.0/spec/standard-webhooks.md)。 |
| WR06 | receiver 需尽快响应并异步处理。**Skill MUST** | 在签名有效且 inbox durable commit 后 ACK；ACK 后业务失败由自己的 retry/outbox/DLQ/reconciliation 处理，不能依赖 provider 会再投。对 queue/backlog 满、数据库 outage 选择 reject retry / 503 / provider signal 并限定容量保护；重试风暴限速但不静默丢弃。 | GitHub profile 中 10 秒目标；不能跨 provider 套用。 |
| WR07 | 有 poison payload / handler 业务永久失败。**Skill MUST** | 分开 transport invalid（签名/schema）和已认证业务 poison。定义 reject/no retry、park/DLQ、最大处理次数、retry-after、operator redrive、修订代码后恢复、payload 敏感字段与 retention；redrive 保留原 event identity 并生成新 processing attempt，不覆盖历史。 | 自有 receiver 处理 profile。 |
| WR08 | 有 receiver result/receipt API 或 audit。**Skill MUST** | 提供/内部记录 receipt 至少含 provider/source、authenticated event ID、attempt/delivery ID（如有）、received/processed times、signature key version、state、failure class、next retry、retention。避免存 secret/signature 原文/PII；状态查询受租户授权。存储 retention 不得短于最大 provider redelivery/replay window 与去重窗口。 | Provider 官方 delivery API/retention；未知则列为待定，不猜默认。 |
| WR09 | 可能乱序/批量重复/迟到 event time。**Skill MUST** | event time 与 receive/process time 分开存。以 aggregate revision/sequence 控制状态迁移；旧 revision 忽略或记账；有 gap 时暂存并 fetch canonical state/reconcile，不用 wall clock 代替业务顺序。batch 按 item 认证/结果规则处理，明确部分失败 ACK 行为。 | GitHub 说明可能 out-of-order：[troubleshooting](https://docs.github.com/en/enterprise-cloud%40latest/webhooks/testing-and-troubleshooting-webhooks/troubleshooting-webhooks)；provider-specific。 |
| WR10 | multiple secret/key versions。**Skill MUST** | keyset scope 绑定 provider + endpoint + tenant；验证器只尝试已配置的 active/overlap key，不接受请求指定任意 key URL/kid 作为信任源。轮换窗口并行验证、旧 key revoke、unknown key id、泄露与审计均纳入 positive/negative case。 | GitHub secret storage / Standard Webhooks rotation profile；参 [signatures.md](signatures.md)。 |
| WR11 | receiver 在公网。**Security MUST（设计门槛）** | 通用 limits/auth 按 shared security 定义；Webhook-specific 网络层仍需限连接/body/read duration/concurrency，按可靠源限速且不信任任意 forwarded header。IP allowlist 仅为签名外的附加层并需维护 CIDR；不在错误/日志泄露 signature/key/payload；拒绝畸形 content-encoding/decompression bombs。 | [OWASP API4:2023 resource consumption](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/)、provider security guidance。 |

## “已接收”成功响应合同

成功响应只在已验证身份且事件/处理工作已可靠持久化后发出；它可以表示“durably accepted”，不必等完整业务处理结束。若 API 声称“processed/completed”，必须等对应副作用与完成记录都持久提交。客户端超时导致确认丢失时，sender 会重发；receiver 必须能用同一身份返回稳定已接收/已完成结果。
