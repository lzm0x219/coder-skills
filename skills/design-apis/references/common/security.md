# 跨信任边界的安全契约

触发：调用来自不可信主体、涉及租户/身份/秘密/外部目的地，或会消耗可滥用资源。这里交付可由调用方依赖的安全契约和拒绝路径；完整威胁建模、密钥管理和部署验证属于项目安全实现。`MUST` 默认是本 Skill 的设计要求，外部协议强制仅在采用该机制时成立。

| ID / 条件 | 具体要求 | 消费证据 / 边界 | 一手依据 |
| --- | --- | --- | --- |
| CS01 / 受保护资源 | MUST 为每个操作定义主体、租户、对象及权限来源；认证成功不代表对象访问获准。ID 是否可猜与授权独立。 | 跨租户的单对象/列表/批量/游标/下载拒绝；允许与拒绝均核验。 | [OWASP API1:2023](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)。 |
| CS02 / 字段可读写范围不同 | MUST 明确字段级响应投影及输入许可，含关系对象和批量项；通用模型绑定不得赋予管理字段写权限。 | 越权字段读写、嵌套对象、别名/批量绕过；不以顶层权限代替。 | [OWASP API3:2023](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/)。 |
| CS03 / 多角色或控制面 | MUST 分开订阅管理、执行、重投、取消、删除、导出等操作权限及再次校验时点；隐藏入口不构成权限。 | 同主体可读但不可管理/重投；旧角色凭据不能扩大功能。 | [OWASP API5:2023](https://owasp.org/API-Security/editions/2023/en/0xa5-broken-function-level-authorization/)。 |
| CS04 / 接收 token | MUST 声明认证 scheme、可信发行方/受众或目的服务、权限 scope、过期与刷新/撤销行为；具体 token 格式按 adopted profile 验证；代表其他主体调用同时读 CS16，OAuth 令牌重放与刷新同时读 CS17。 | 错 audience/过期/错误 scope 与合法 token；不得仅 decode 后信任。 | OAuth采用时：[RFC 6750 §5](https://www.rfc-editor.org/rfc/rfc6750#section-5)、[RFC 9700 §2](https://www.rfc-editor.org/rfc/rfc9700#section-2)。 |
| CS05 / Bearer 秘密跨网络 | MUST 使用所选协议要求的受保护传输并决定存储/缓存边界；采用 OAuth 时客户端 MUST NOT 按 RFC 6750 §2.3 在 URI query 传 access token；诊断/trace/错误/请求快照不泄露秘密。其他 token profile 的传递位置另查其规范。 | 重定向、日志、异常 cause、请求快照及缓存查看是否泄漏。 | [RFC 6750 §2–5](https://www.rfc-editor.org/rfc/rfc6750#section-2)、更新强制条款 [RFC 9700 §4.3.2](https://www.rfc-editor.org/rfc/rfc9700#section-4.3.2)。 |
| CS06 / 浏览器凭据 | MUST 定义 origin、cookie/CORS/CSRF 与调用方法的组合；允许跨域读取不等于允许跨站写。 | 不可信 origin、simple request、无CSRF标识的带cookie写；拒绝发生在副作用前。 | 风险设计：[OWASP API安全](https://owasp.org/API-Security/editions/2023/en/0x11-t10/)；具体HTTP/GraphQL机制见类型页。 |
| CS07 / 用户提供外部目的地 | MUST 列 scheme/host/port/解析/redirect/代理的验证边界及失败响应，防止初验后地址变化；URL形状合法不等于目标安全。 | private/link-local、IPv6、重定向、DNS变化和验证后发送差异。 | [OWASP API7:2023](https://owasp.org/API-Security/editions/2023/en/0xa7-server-side-request-forgery/)；Webhook具体机制见其receiver/sender页。 |
| CS08 / 昂贵或高容量操作 | MUST 定义限额主体/窗口、请求/响应/嵌套/并发/批量/流/解压/缓存与暂存内存/存储边界和限额错误；限制须在昂贵分配或副作用前生效，最终队列有界不等于处理中间缓冲有界。具体上限由项目决定，未知写候选。 | 恰好边界及超界，合法小请求聚合超成本、大批量暂存；消费者有有界退避/调整路径。 | [OWASP API4:2023](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/)为风险依据，本条中间缓冲门槛为 Skill 综合要求。 |
| CS09 / 重放或签名身份 | MUST 写签名覆盖项、验证顺序、nonce/时间/身份作用域、轮换与重放保留边界；有效体签名不认证未签 metadata。 | tamper、过期、重复、缺少签名、旧key及异租户；异常也不泄密。 | 采用HTTP签名时：[RFC 9421](https://www.rfc-editor.org/rfc/rfc9421)；提供方profile优先。 |
| CS10 / 同一资源不应泄露存在 | MUST 决定不存在与无权访问是否一致、是否可缓存，以及错误明细/延时允许暴露的边界。 | 404/permission差异为具体项目取舍；旧客户端仍可正确恢复。 | 设计；HTTP隐藏许可：[RFC 9110 §15.5.4](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.4)。 |
| CS11 / 外部数据进入可信流程 | MUST 保留来源可信级别、验证阶段与权限决定；第三方错误、header、event type、SQL结果/插件输出不能直接升级为授权事实。 | 未签头、错误对象、第三方payload合法但业务身份错误；拒绝/隔离有证据。 | [OWASP API10:2023](https://owasp.org/API-Security/editions/2023/en/0xaa-unsafe-consumption-of-apis/)。 |
| CS12 / 安全默认值或兼容变更 | SHOULD 采用最小权限和显式能力启用；MUST 评估新默认、兼容旧模式或“调试”入口对访问范围的影响，安全修复破坏兼容时记录迁移决定。 | 默认配置的失败路径、新旧权限主体矩阵；不得用隐藏实现推断安全保证。 | [OWASP API8/API9](https://owasp.org/API-Security/editions/2023/en/0x11-t10/)；[兼容](evolution.md)。 |
| CS13 / 可被自动化滥用的业务流程 | MUST 识别预订、购买、优惠、批量发布、注册或类似流程中即使鉴权成功/低资源成本仍会造成的业务损害；给出业务限制主体、累计范围、拒绝/补救和可信自动化调用的约束。按真实风险选择措施，不一律要求 CAPTCHA 或禁脚本。 | 合法单次、跨请求累计、跨账号/批量及正式机器消费者；资源限流通过不代表业务防滥用通过。 | [OWASP API6:2023 / How To Prevent](https://owasp.org/API-Security/editions/2023/en/0xa6-unrestricted-access-to-sensitive-business-flows/)是风险建议，本条为设计要求。 |
| CS14 / 多入口/环境/版本对外提供 API | MUST 列完整 host/入口、环境、版本、访问者、交换数据与敏感程度，包含旧版/测试/调试入口；新版本安全改进需决定旧入口回移、隔离或退役。 | 入口清单与公开契约/部署事实对照；只检查当前 schema 不证明其他入口安全。 | [OWASP API9:2023 / How To Prevent](https://owasp.org/API-Security/editions/2023/en/0xa9-improper-inventory-management/)；设计可列未知实际环境，部署核验另行执行。 |
| CS15 / 提供登录、凭据恢复/轮换、会话或敏感身份变更 | MUST 将恢复与变更操作纳入认证流程契约，定义凭据失效/再认证、重放/爆破限制和拒绝后的可观察状态；不要只保护普通数据入口。按实际人/机器消费者选择措施，不自动强加 CAPTCHA 或密码模式。 | 合法恢复、失败/过期/复用、连续尝试、轮换前后凭据及敏感变更；实际认证服务和密码学实现另验。 | [OWASP API2:2023](https://owasp.org/API-Security/editions/2023/en/0xa2-broken-authentication/)为风险建议，本条为设计要求；具体scheme按其官方协议。 |
| CS16 / 跨主体委托、冒充或代表用户调用 | MUST 区分被代表的主体（subject）与实际执行者（actor），声明采用 delegation 还是 impersonation、下游按哪些已验证身份与权限判权，以及审计能看到谁；不要求所有 API 支持 Token Exchange 或所有 token 都含 actor。冒充模式下执行者可能对下游不可见，须如实注明。采用 RFC 8693 JWT `act` 时，协议 MUST 只以顶层 claims 与当前 actor 作访问控制；嵌套历史 actor 仅供信息，不授予权限。 | 直接调用、合法委托、错误 actor/越权 scope、执行者不可见的冒充；不把未验证的“代表谁”metadata 当授权。审计字段及保留范围按项目政策。 | [RFC 8693（2020）§1.1](https://www.rfc-editor.org/rfc/rfc8693.html#section-1.1)定义两种语义；[§4.1](https://www.rfc-editor.org/rfc/rfc8693.html#section-4.1)约束 JWT `act`。身份/审计决策清单是 Skill 要求。 |
| CS17 / 采用 OAuth access/refresh token | MUST 记录令牌是否绑定发送方及其验证责任。按 BCP 240，授权与资源服务器 SHOULD 采用 sender-constrained access token（如 mTLS 或 DPoP）；偏离时注明架构限制与剩余重放风险，audience 校验不能代替持有者证明。采用绑定时，写明 token—密钥绑定、proof 验证与防重放、失败拒绝及密钥轮换行为，机制细节按 adopted profile，不混用 mTLS 与 DPoP 保证。采用 OAuth 并向 public client 签发 refresh token 时，RFC 9700 / BCP 240 要求授权服务器 MUST 采用发送方约束或 refresh token rotation 检测重放；选轮换须保留 token 家族关系，检测到已失效 refresh token 复用后撤销该家族当前有效的 refresh token，让合法客户端重新授权，不一律推定撤销所有 access token。 | 合法持有者、错密钥/无效或重放 proof、旧 refresh token 复用；机制不支持/未部署标为限制或未验证。绑定不防止 token 与对应密钥同时泄露。 | [RFC 9700 / BCP 240（2025）§§2.2.1–2.2.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.2)、[§4.10.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.10.1)、[§4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2)。access token 是 SHOULD，public-client refresh token 条件命中时是 MUST。 |

纯本地算法且没有不可信输入/外部资源时，可记录对应分支不适用；对象/字段授权不能因 API 是 RPC、SDK 或事件消费而省略。
