# HTTP API 设计规则

适用于通常的 HTTP 请求与响应接口。先核对项目既有契约和 HTTP/OpenAPI 版本；GraphQL 的执行错误与部分结果另按 [GraphQL 规则](graphql.md)，不能直接套用本页的普通错误响应建议。

## 协议语义

1. 按调用方要求的效果选方法：`GET`、`HEAD` 是安全方法，不承载删除或付款等写入意图；`PUT`、`DELETE` 和安全方法具有幂等语义。`POST`、`PATCH` 不因方法名自动具备幂等性；若支持重试，明示重复请求识别和结果查询方式。依据：[RFC 9110 方法语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2)。
2. 状态码表达 HTTP 层面的结果：已创建资源可用 `201` 并提供定位方式，已接受但尚未完成可用 `202`，成功且无响应内容可用 `204`；错误不要一律返回 `200` 并藏在响应体中。依错误性质区分请求无效、无权限、冲突、前置条件失败和服务器故障，不为追求状态码数量而制造类别。依据：[RFC 9110 状态码](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)。
3. 并发写入可能覆盖他人修改时，设计版本或条件请求。采用 `ETag`/`If-Match` 时明确比较对象与更新冲突的 `412` 结果；不要只在文档里声称“乐观锁”而没有调用方可传的条件。依据：[RFC 9110 条件请求](https://www.rfc-editor.org/rfc/rfc9110.html#section-13)。
4. 需要缓存时定义新鲜度、验证和共享范围；带个人数据的响应核对 `Cache-Control` 等缓存指令。`private` 与 `no-store` 有不同语义，`no-store` 本身也不能保证数据保密。依据：[RFC 9111 HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html)。

## 契约设计与核验

5. 为每个操作写清路径标识、查询参数、请求体、响应体和相关头字段的职责；对字段说明必填、缺省、`null`、允许值与验证失败的结果。标识符会被调用方持久化时，定义稳定性，不让调用方依赖未承诺的内部编码。
6. 错误提供稳定、可机读的类别和安全的说明。项目已有错误封装则沿用；需要新建 HTTP 错误表示时可评估 [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html) 的 `type`、`status`、`detail` 等字段，不把它当成所有 HTTP API 的必选格式。
7. 集合接口定义默认与最大页大小、稳定排序依据、分页位置、过滤语义及数据变动时的遍历结果。游标若为不透明值，就不要要求调用方解析；不要承诺未提供一致性机制的固定总数或无重复翻页。
8. 使用 OpenAPI 时固定项目采用的规范版本，在同一契约中描述参数、请求体、成功与错误响应、安全要求和可运行示例。运行对应版本的校验器，并用示例对照实现；Schema 校验通过不能证明状态码、权限或副作用语义正确。依据：[OpenAPI Specification](https://spec.openapis.org/oas/)。

## 落地时填写

为**每个操作**写一行契约，不能只写“提供增删改查”：

| 项 | 必须给出的具体值 |
| --- | --- |
| 入口 | 方法、URI 模板、内容类型；路径与查询参数各自的含义 |
| 输入 | 字段类型、必填/可选、缺省、`null`、长度或范围；无效输入的结果 |
| 成功 | 状态码、响应头与响应体示例；若异步，完成状态的查询入口 |
| 失败 | 调用方会遇到的状态码、稳定错误类别、是否能重试 |
| 权限 | 谁能调用、目标资源不可见时如何响应；无鉴权时明确写“公开” |
| 一致性 | 写入何时可见；重复请求、超时和冲突怎样处理 |

按实际操作选语义，而不是照搬一组固定端点：

| 情况 | 具体规则 | 核验 |
| --- | --- | --- |
| 只读取 | 用安全方法；`GET` 不执行调用方请求的写入 | 重复请求不改变目标业务状态 |
| 创建且已完成 | 可用 `201`；定义新资源的标识与定位方式 | 响应中的标识能用于后续读取 |
| 已接收、仍在处理 | 可用 `202`；定义查询完成/失败的入口和保留期 | 调用方不会把 `202` 当作最终成功 |
| 完整替换已知资源 | `PUT` 的重复请求保持相同预期效果 | 相同输入重发不会创建第二份资源 |
| 局部修改 | 若用 `PATCH`，指定补丁格式与原子性；不假设它天然幂等 | 部分失败不会留下半次补丁；依据 [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html) |
| 防止覆盖并发更新 | 若用 `ETag`/`If-Match`，记录版本产生方式、比较范围与 `412` | 旧版本写入不能覆盖新版本 |
| 限流 | 若提供限流反馈，`429` 说明限制范围；`Retry-After` 仅在能给出等待时间时填写 | 客户端可决定何时重试；依据 [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html) |

示例（仅演示并发更新契约）：`PUT /profiles/42` 携带 `If-Match: "v7"` 和完整资料；成功返回 `204` 与新 `ETag`，旧版本返回 `412`，无权访问返回项目既定的权限错误。评审时必须检查 `204` 无响应体、旧版本确实无法覆盖新版本，并说明 `v7` 对调用方是不透明版本值。

可复查的[条件更新契约与正反样例](../tests/fixtures/http-profile/contract.md)演示如何把前置条件落实到 OpenAPI；模型检查不代替真实服务的并发写入验证。
