# 设计 API 契约

把调用者能够依赖的行为作为设计对象。先确认调用方、使用场景、接口形态、稳定性承诺和项目现有约定。修改已有 API 时，读取契约源文件、实现、已知调用方和相关测试，区分既有行为、拟议变更与未知事实；不要把内部存储结构直接当成外部契约。协议或工具的版本敏感规则以项目所用版本的权威资料核验。

## 契约规则

1. 每个操作写清前置条件、输入、成功结果、可见副作用和失败结果。字段说明包含必填性、缺省值、空值与缺失的区别、约束和含义；单位、时区、精度或顺序会影响调用方时，明确写出。不要让调用方从示例猜测规则。
2. 错误须让调用方知道如何处理：提供稳定的机器可识别类别、可读说明和必要的安全上下文，区分可重试、应修正输入、权限不足等情形。不要要求调用方解析错误文案，也不要暴露内部堆栈或敏感数据。
3. 对可能重复、并发或超时的调用，明确副作用是否可安全重试、重复请求如何识别、冲突如何报告，以及“请求已执行但响应丢失”时调用方怎么办。对集合或高成本查询，明确分页、排序、过滤及限制；只引入任务实际需要的机制。
4. 变更已有接口时，从调用方视角分别检查源码、传输格式和行为兼容性。删除或重命名、增加必填输入、改变默认值、字段含义、错误类别或可见顺序，都应先视作潜在破坏性变更；新增字段也要考虑严格解析器或穷举分支。给出受影响调用方、兼容方案与迁移期限；无法核实的影响标为未知。可参考 [AIP-180](https://google.aip.dev/180) 的兼容性分类，但以项目契约为准。
5. 在契约中说明调用身份、操作权限与敏感字段边界，但具体安全方案交给对应安全设计任务。接口形态不同，不能把 HTTP 的方法、状态码或资源风格强加给 RPC、语言级 API 与事件协议。

先确定项目采用的协议或规范版本。区分协议的强制要求、官方格式规范和生态设计建议；现有项目风格可决定建议项，但不能把违反已采用协议的行为称作符合规范。按当前接口类型选读对应规则；一个任务跨多种接口时再组合阅读：

- 一般 HTTP 请求与响应：[HTTP API](references/http.md)。
- GraphQL schema、查询与变更：[GraphQL API](references/graphql.md)；仅在处理 HTTP 传输时再读 HTTP 规则。
- RPC 方法及消息，使用 Proto 时包括其演进：[RPC API](references/rpc.md)。
- 库、SDK 和框架的公开程序接口：[程序接口](references/library-sdk.md)。
- 消息系统中的事件契约：[事件 API](references/events.md)。
- 发送 HTTP Webhook，或接收第三方 Webhook：[Webhook API](references/webhooks.md)；同时参考 HTTP 规则中适用的部分。

参考文件中的规则按触发条件应用。交付前逐条核对命中的 `MUST`，指向契约中的具体值、示例或验证证据；示例本身也须满足命中的规则，冲突时先修示例。无法核实的事实与行为列为未决，不写作通过。设计或重命名公开 SDK 名称时，执行[命名准入](references/library-sdk/naming.md)，用相反解释和信息不足场景检查结论；多个名称都符合事实时，可记录明确的设计取舍，但不得把取舍说成规范唯一推出的事实。不要用“按需处理”“支持错误”“考虑兼容”代替可由调用方依赖的行为。

## 交付与核验

采用项目已有的契约载体，例如 OpenAPI、Proto 或公共类型定义。HTTP、GraphQL、RPC、事件及 Webhook 的具体提案按[协议接口交付](references/protocol-deliverables.md)提交契约源文件、调用方或消费方样例及独立的验证结论。目标语言已确定的具体库/SDK/框架程序接口提案，按[程序接口](references/library-sdk.md)的设计期交付要求提供可检查的公开声明与消费者调用点；接口文档补充类型无法表达的行为。仅讨论概念、只做现状评审或目标语言未定时，按任务范围交付相应的模型、结论或文档，不制造无法验证的代码。没有既定载体时，至少交付操作、数据、成功与失败示例、兼容决策及未决问题。用一个正常调用和一个关键失败或边界场景走查：调用方能否仅凭契约正确发起调用并处理结果？多种失败可能同时发生时，再走查错误优先级。规范校验器与类型检查只验证格式和类型，还需核对语义、示例、实现与调用方行为是否一致。

用户要求实现时，继续完成对应代码与适当验证；只要求设计时，交付可供实现和评审的契约，说明尚未运行验证的行为。不要把拟议契约写成已上线事实。
