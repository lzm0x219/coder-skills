# 系统化 API 设计能力的验收与评分

适用范围：本页评整个 Skill 的设计与使用能力。用户只审查规则质量时使用[规则专项审查](rules.md)，分别报告四个规则维度；本页实际消费/独立使用项不自动变成规则缺陷。规则专项结果不替代整体能力验收。

评分对象是整个 `coder:design-apis` 的规则体系及设计期使用能力。覆盖[类型与维度矩阵](../../../skills/design-apis/references/coverage.md)。未收录的具体协议必须有读取其权威版本、补差异和验证消费者的路径；九种接口形态不是所有协议产品的有限枚举。

## 满分所需证据

| 维度 | 0 分 | 1 分 | 2 分必须具备 |
| --- | --- | --- | --- |
| 体系与覆盖 | 混淆边界或遗漏接口形态 | 有分类但关键维度/分支无规则 | HTTP、GraphQL、RPC、程序接口、事件、Webhook、实时、CLI、查询均有路由；十二维度有权威规则位置；复合控制/数据面、原生/包/扩展者、具体协议 profile 及未收录技术有适用路径。逐项覆盖审查没有未处理的关键空白。 |
| 行业依据与规则质量 | 口号或规范失真 | 有来源但缺触发/行为/证据或有错误强制 | 规则给出条件、具体动作、失败/恢复、等级与证据；一手资料版本和对应章节可核验，规范/格式/生态/项目综合分清。命名与语义不会凭同义词或猜测改事实；来源冲突按对象/版本处理，产品数值不是伪行业标准。 |
| 交付与验证合同 | 只有设计文案或虚假通过 | 载体/消费者/未决之一不完整 | 各接口形态有主契约与可复跑检查的要求；正常、关键失败、旧消费者和恢复有追踪。事实、候选、未知与静态/模型/运行/部署状态准确分开。未给旧签名时不制造既有契约；样例与公开声明兑现同一行为。 |
| 实际消费与反例 | 展示或自证标记 | 只有单一窄案例或词法检查 | 既有回归与新增分支包含真正解析/编译/子进程/消费者执行，关键错误被工具或消费行为拒绝。协议间、旧严格解析器、部分成功、权限、字节身份、并发/资源/流和目标语言差异有有界证据；模型不冒充真实 broker/平台。设计 Skill 不因没有生产部署而要求伪造结果。 |
| 独立使用与写作 | 无独立使用或不可发现规则 | 只查固定产物或每任务加载巨型清单 | Fresh agent 只获原始任务、Skill 和必要事实完成多类型/新增分支；审阅实际契约及消费者，保留首次缺陷、修复与复测。入口短且按条件路由，共享含义单一权威，操作与证据就近组织；独立评测者不会得到期望答案。 |

每项 2 分须满足整行。半分只表示确有证据且存在具体缺口；总分不得掩盖阻断。以下任一未解决问题禁止满分：关键协议违规、编造既有事实、条件指针遗漏实际接口、无法定位的强制规则、主契约/消费者不一致、关键恢复未设计，或把未验证称为通过。规则条数、链接数量和文本匹配不是质量分。

## 证据与 Jev

审查先读取当前文件及真实工具结果，再记录 `维度/规则 → 契约/消费者 → 检查结果 → 未覆盖/未决`。每份证据只证明对应任务、材料与当时 Skill；不能称新增规则已由旧代理执行。执行代理只看原始任务，评审材料独立保存；有问题后的定向修复属于第二阶段，不算首次盲测全对。

若用户明确要求 Jev 认可整体评分，向 Jev 提供已核实的证据、判断选项和真实限制；低置信度、`escalate` 或证据不足时继续调查。没有新事实时不重复提问争取有利结论，不舍入分数。完成标准以当前用户要求为准。

满分是这套系统化规则与实际设计期证据的验收判断，不声称所有未来任务成功率为 100%，也不替代真实服务、安全、容量、ABI、发布或部署验收。评测方法参考[OpenAI Evaluation Best Practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)。
