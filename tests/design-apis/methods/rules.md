# API 规则专项审查

用户询问规则是否完整、准确、具体或符合行业最佳实践时使用本流程。审查对象是当前 Skill 与 references；[整体能力准则](capability.md)另评实际设计、消费者执行和独立使用。两种结果分别报告。

## 四个维度

| ID | 检查对象 | 通过所需证据 | 可定位的不足 |
|---|---|---|---|
| coverage | 类型、设计维度、条件分支和路由 | 逐项列适用范围、权威规则位置及不适用理由；未列技术有取得官方版本和补差异的路径 | 某个已声明适用分支无规则或必要指针，给出缺失对象与应落位置 |
| accuracy | 外部规范及推荐是否转述准确 | 目标版本、章节、一手原文与当前规则对照；区分协议 MUST/SHOULD/MAY、生态实践和 Skill 自定要求 | 明确的条件、等级、责任主体或语义不符；指出两侧原文和影响 |
| execution | 规则是否能指导设计与审查 | 触发条件、具体决定/动作、适用的失败或恢复、交付物和验收证据；无法执行时有阻断或补事实路径 | 指出哪项决定/动作/失败处理/证据要求缺失，以及调用方无法作出的判断 |
| traceability | 每个外部主张是否有可靠依据 | 一手 URL、版本/profile、具体章节与取得日期；滚动文档注明目标工具链；综合要求说明推导 | 链接不支持主张、版本/profile不匹配或出处无法核验；明确待补事实 |

运行证据是规则要求设计者交付的内容。审查“规则是否写清应验证什么”时，服务、broker 或 SDK 尚未实现本身不构成规则缺陷。需要运行才能核实的主张列为待核实；真实行为是否满足合同归入整体能力或产品验收。

## 执行步骤

1. **固定范围。** 记录当前源文件 SHA、适用类型/维度和选择的审查单元。完整审查逐规则维护覆盖台账；抽查明确列未审部分。历史结果只说明当时的文件。
2. **收集事实。** 每个单元附当前规则路径、行号和原文；外部主张附一手资料版本、章节、取得日期及核对摘要。先核验资料，再形成判断选项。
3. **核对四维。** 同一单元可命中多个维度；每个判为不足的条目写具体问题、影响、建议改法和证据。不适用项说明条件。资料不足使用“待核实”。
4. **调用 Jev。** 提交一个单元的必要事实和有界问题，可批量处理相互独立的单元。选择项为“通过”、已核验缺陷的 ID 或“待核实”；已知缺陷必须给 Jev 同样的两侧证据。Jev 负责判断，Codex 负责资料、缺陷描述与修改。
5. **处理返回。** 记录原始 answer/confidence/escalate。低于 0.7、escalate 或不能定位的笼统扣分归为待核实；补事实后再判，或附独立复核记录由 Codex 作结论。泛化分数不生成缺陷，也不触发新增测试工程。
6. **修复与验收。** 按已定位缺陷修改其权威规则，复核修改前后与规范一致。检查当前引用、位置和版本；适当的载体检查只验证相关规则。已有事实不变时沿用结果。

## 缺陷与报告合同

缺陷必须包含：`id / dimension / rule(path, lineStart, lineEnd, quote, sha256) / authority(url, version, section) / problem / impact / fix / evidence`。纯 Skill 要求的 authority 写本地权威依据，说明它是综合要求，不能冒称外部协议。待核实项写缺少什么事实及取得路径。

每个单元结论仅为通过、有定位的缺陷、待核实。结论中分别列覆盖范围、具体缺陷、待核实项和未审部分。只有完整覆盖台账与所有适用单元均闭合，才讨论整个规则体系的结论；局部通过保持局部范围。已有整体评分保持其原定义与历史结果。

[报告校验器](../checks/review_rules.py)检查位置、哈希、证据字段和结论一致性：

```sh
rtk proxy python3 tests/design-apis/checks/review_rules.py <规则专项报告.json>
```

exit 0 表示报告结构与本地证据一致；规范语义是否正确仍由上述审查核实。校验器拒绝无定位的缺陷、把低置信度结果当通过、把运行验证条件放进本专项，以及用局部审查宣称全规则通过。
