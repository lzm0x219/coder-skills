## 触发与边界

建议 description：在既定行为和兼容约束下重构代码结构，明确改善目标，分步调整模块与依赖，并验证受影响消费者及公开契约。

典型请求：拆分难维护模块；重新设计目录与文件名；消除重复实现；整理依赖方向；在保持公开 API 的条件下调整内部结构。

- 明确结构目标的重构由本项承接；只有“看看有哪些架构问题”时先形成有证据的候选，不能自行扩大修改范围。
- 用户要求行为变化时，区分重构部分与功能变化，分别列出验收条件。
- 故障复现与修复归 fix-bugs；固定差异审查归 review-changes；依赖升级、系统迁移另有终点，不能借重构一并实施。
- 小范围重命名直接执行必要核验，不强制套用完整仪式。遵守项目及会话既有方案确认要求，不新增普遍审批关卡。

## 必须产生的实操价值

先指出实际维护摩擦，例如同一变化要修改多个位置、领域知识泄漏、依赖循环或模块边界与职责不符。用真实调用方与变化实例支持目标，不把文件更少、函数更短或行数下降当作成功证据。

明确哪些观察必须兼容：输入输出、错误、序列化、事件顺序、副作用、公开导出、类型声明，以及任务相关的资源生命周期和性能约束。仅选取本次改动可能影响的项目；不机械穷举。

目录重设计必须同时考虑职责、命名、依赖方向与消费者路径，不能把原文件平切成多个文件就声称结构改善。保留合理的项目风格，只有可解释的收益才增加抽象。

## 状态与退出条件

| 状态 | 执行动作与证据 | 转移或退出 |
| --- | --- | --- |
| S0 固定范围 | 核对仓库、已有改动、用户目标、允许改变的行为；列出范围和非目标 | 目标歧义会改变方案时澄清；否则进入 S1 |
| S1 建立兼容基线 | 追踪公开入口、真实消费者和受影响路径；运行适当基线检查，记录已有失败 | 关键行为无可用证据则补特征测试或对照样例；无法建立时说明缺口并缩小范围 |
| S2 选定结构方案 | 对照当前与目标模块职责、文件布局、依赖方向；说明收益、代价、验证方式 | 遵守已有确认要求；目标无法改善或成本不合理时交付依据并停止实施 |
| S3 分步实施 | 按可独立验证的切片改动，同步导入、导出与内部引用；保留他人修改 | 每个切片检查受影响路径；出现回归回到该切片定位，避免叠加新变化 |
| S4 核验结果 | 对照前后契约与消费者，执行相关测试、构建、类型及必要运行检查；核对目标结构收益 | 新失败修复后重验；证据不足不能标记兼容已验证 |
| S5 交付 | 报告结构变化、改善依据、检查结果、已有失败及未验证项 | 范围完成且必要验证通过才完成；发布、合并与安装仍按已有授权处理 |

基线已有失败时，记录原结果并分离本次影响；不得把已有失败悄悄归零。无法运行原环境时，可以使用替代验证，但明确其覆盖范围。对照测试通过不等于证明所有可观察行为等价。

| 案例 | 必须观察到的行为 |
| --- | --- |
| 公开 TypeScript 库目录重设计 | 实际重建职责与布局，消费者继续可用，公开导出和生成声明无未经授权的变化 |
| 有状态异步模块拆分 | 保持事件顺序、取消与清理行为；验证包含能捕捉时序错误的反例 |
| 重复实现合并 | 正常、边界、错误及副作用语义保持；避免引入没有实际使用价值的抽象 |
| 基线已有失败 | 正确识别并记录旧失败，另证本次受影响路径，不虚报全部通过 |
| 工作区含用户修改 | 保留已有修改，只处理目标范围；无法安全分离时说明阻塞 |
| 只读请求或无收益候选 | 交付分析，不越权修改、不为了满足流程强行重构 |
| 原环境缺失 | 报告证据缺口与替代验证限制，不宣称原场景兼容已验证 |
| 无 Skill 名称的自然请求 | 正确选择重构能力；对修 bug、功能开发、差异审查反例不过度触发 |

验收分别记录任务完成、结构收益、兼容证据、范围与权限、路由表现。可观察行为未经授权变化、覆盖用户修改、只读越权、伪造检查结果任一出现即不通过。静态格式校验与行为评测分层报告；限定案例通过不能扩张为任意项目可靠。
