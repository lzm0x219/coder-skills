# Coder 软件工程完整覆盖设计

状态：**规划草案**。目前仓库实现 `coder:master`、`coder:design-apis` 和 `coder:fix-bugs`；`fix-bugs` 已完成[限定范围的独立评测](../skills/fix-bugs/tests/evaluations/fix-bugs-2026-09-30.md)，`design-apis` 仍待完整真实任务验证。下表列出 43 项覆盖任务的英文工作名与当前状态；它们不等于 43 个待创建目录。

## 覆盖目标

`coder` 以用户要完成的目标为入口，覆盖软件从需求到退役的通用工程任务。这里的“完整覆盖”指每类任务都有明确的处理路径：由已实现的专业 Skill 处理、由 `master` 使用智能体的常规能力完成，或明确指出当前缺少的资料或能力。它不表示每种语言、框架、行业法规都有内置专门 Skill。

本清单以 [IEEE SWEBOK V4.0a](https://ieeecs-media.computer.org/media/education/swebok/swebok-v4.pdf) 的知识领域检查生命周期缺口；SWEBOK 是覆盖参考，不是 Skill 与知识领域的一对一映射。一个专业 Skill 应围绕可识别的用户目标，明确触发条件、输入、产物和成功标准；相邻目标确有不同的工作方法时才拆分。参见 [OpenAI Skill 编写指南](https://developers.openai.com/plugins/build/skills)。

## 结构与路由

- `master` 是唯一总入口。它尊重用户明确指定的 Skill，并根据当前任务选择一个主 Skill；另一项能力仅在任务确实需要不同判断时参与。
- 下表按生命周期分组以方便审查覆盖，不作为目录层级。实际 Skill 仍平铺于 `skills/<skill-name>/SKILL.md`。
- 每项先作为**覆盖单元**。英文工作名便于讨论和交叉引用；“已实现”表示已创建 Skill 文件，“优先候选”表示值得验证独立触发、方法和产物，“覆盖项”先由 `master` 或相邻 Skill 承接。已实现不等于经过真实任务验证。
- 技术栈、职位、工具和行业规则作为适用条件或按需资料。需要版本敏感或高风险结论时读取对应权威资料，不把某个生态的做法写成通用规则。

## 覆盖任务与职责

每行描述一个必须能处理的用户目标。工作名采用动词在前的简短英文；创建 `SKILL.md` 后成为 Skill 名，真实任务验证另行记录。

### 需求、理解与规划

| 英文工作名 | 状态 | 核心职责与可验收结果 | 与相邻能力的边界 |
| --- | --- | --- | --- |
| `explore-codebase` | 覆盖项 | 查明现有模块、调用路径、约束与测试入口，给出文件依据。 | 说明当前状态，不替用户作新设计。 |
| `triage-issues` | 覆盖项 | 核实外部提交的缺陷、需求或 PR，判定下一步状态并形成可接手的任务简报。 | 处理未经整理的输入；由本项目规划产生的任务直接进入工作规划。 |
| `define-requirements` | 优先候选 | 明确目标、范围、限制、非功能要求和验收条件。 | 确定要解决什么，不预定具体架构。 |
| `model-domain` | 优先候选 | 定义业务概念、关系、规则与不变量。 | 处理业务语义，不设计持久化表。 |
| `assess-options` | 覆盖项 | 比较可行方案、成本、技术风险和待验证假设。 | 给出选择依据，不拆实施任务。 |
| `prototype-ideas` | 覆盖项 | 针对一个设计疑问制作最小可运行原型，记录观察结果与可采纳的决策。 | 用实验回答问题；不把原型直接视为正式实现。 |
| `plan-work` | 覆盖项 | 拆分交付步骤、依赖、风险和检查点。 | 使用已明确的目标，不重写需求。 |
| `track-delivery` | 覆盖项 | 跟踪进度、范围变化、依赖、风险和决策，调整计划并留下可核验状态。 | 管理持续执行，不代替首次任务拆分或软件发布。 |

### 工程设计

| 英文工作名 | 状态 | 核心职责与可验收结果 | 与相邻能力的边界 |
| --- | --- | --- | --- |
| `design-architecture` | 优先候选 | 确定系统或模块职责、依赖方向、边界与演进路径。 | 决定职责归属，不逐字段定义接口。 |
| `design-apis` | 已实现 | 定义调用者可见的操作、数据、错误、兼容和版本契约。 | 决定外部契约，不决定内部存储。 |
| `design-storage` | 优先候选 | 设计持久化结构、约束、查询形态与一致性规则。 | 处理存储数据，不代替业务术语建模或内存算法。 |
| `design-algorithms` | 优先候选 | 根据数据规模、操作和资源约束选择数据结构与算法，并核验复杂度或性能假设。 | 处理计算方法，不设计持久化模式。 |
| `design-concurrency` | 覆盖项 | 明确并发边界、共享状态、时序、同步和一致性语义。 | 处理并发正确性，不代替整体模块划分。 |
| `design-ui` | 优先候选 | 设计用户流程、交互状态、响应式行为与无障碍要求。 | 产出交互方案，不替代界面实现验收。 |
| `design-security` | 优先候选 | 识别资产与信任边界，设计授权、隔离和其他防护措施。 | 产出安全设计，不宣称现有代码已安全。 |
| `design-privacy` | 覆盖项 | 设计个人数据收集、最小化、保留、删除和访问边界。 | 处理数据生命周期；法规结论需适用来源支持。 |
| `design-reliability` | 覆盖项 | 设计故障隔离、降级、恢复、容量和服务目标。 | 处理预期故障，不执行线上应急。 |
| `design-observability` | 覆盖项 | 定义日志、指标、追踪和告警应回答的问题。 | 设计可观测信号，不代替故障调查。 |
| `design-tests` | 覆盖项 | 从行为与风险推导测试层级、案例、数据和测试接缝。 | 设计证明方法，不把设计稿当作测试通过。 |

### 验证与质量

| 英文工作名 | 状态 | 核心职责与可验收结果 | 与相邻能力的边界 |
| --- | --- | --- | --- |
| `test-software` | 覆盖项 | 执行与风险相称的测试或检查，报告通过、失败与未覆盖范围。 | 提供运行证据，不把静态结构校验当作业务正确性。 |

| `audit-compliance` | 覆盖项 | 对照适用的法规、许可证、标准与组织政策检查工程证据，标明来源和缺口。 | 依据当前权威资料判断，不凭通用规则作法律结论。 |

### 维护与演进

| 英文工作名 | 状态 | 核心职责与可验收结果 | 与相邻能力的边界 |
| --- | --- | --- | --- |
| `fix-bugs` | 已实现 | 复现问题、定位原因、修复并完成有意义的回归验证。 | 以当前缺陷为范围，不顺带展开无关重构。 |
| `review-codebase` | 覆盖项 | 根据近期变更和实际维护摩擦检查代码结构，给出有文件依据且可排序的改善候选。 | 发现并评估机会；选定后的修改由重构任务承接。 |
| `refactor-code` | 覆盖项 | 在可观察行为受控的前提下改善模块深度、依赖和可修改性。 | 改善内部结构；行为需求另行明确。 |

| `migrate-systems` | 覆盖项 | 规划并执行模式、接口或技术迁移，核验兼容期、回退与旧路径退役。 | 负责一次迁移的终点，不覆盖所有日常发布。 |

## 软件类型与技术栈

任务目标决定主 Skill，软件类型决定需要读取哪些按需资料。同一类 `design-apis` 任务可以用于 Web 服务、SDK 或设备协议，但不能把它们的契约约束混为一谈。

| 软件类型 | 需要按任务补充核验的约束示例 |
| --- | --- |
| Web、移动和桌面应用 | 平台交互规范、设备能力、无障碍、离线和发布渠道 |
| 服务端、分布式系统和云基础设施 | 网络边界、可用性、容量、数据一致性和运行成本 |
| 库、SDK、CLI 和开发工具 | 公共接口兼容、安装分发、跨平台行为和开发者体验 |
| 数据平台、数据处理和 AI 系统 | 数据质量、血缘、可复现性、模型评估与运行监控 |
| 嵌入式、实时和安全关键系统 | 资源与时序边界、硬件验证、故障安全和适用标准 |

这些类型不直接变成同名 Skill。真实任务若有独立且重复的工作方法，再依下述条件增设专门 Skill 或按需参考。

## Matt Skills 的借鉴点（待优化）

以下记录从本机安装的 `ask-matt` 及其关联 Skill 中提取的设计输入。它们是对候选能力的补充依据，不代表照搬 Matt 的完整流程或立即创建目录。其[官方路由说明](https://github.com/mattpocock/skills/blob/main/docs/engineering/ask-matt.md)可供对照；`coder:master` 仍按本项目约定选择实际可用的能力并继续推进任务。

| 来源 Skill | 借鉴的方法 | 在 `coder` 中的承接与待验证边界 |
| --- | --- | --- |
| `triage` | 对外部原始 issue 或 PR 先核实事实，再形成可执行简报；区分它们与内部已拆好的任务。 | 归入 `triage-issues`；状态与产物适配项目现有任务管理方式。 |
| `prototype` | 一个可运行原型只回答一个设计问题，并把观察结果带回正式方案。 | 归入 `prototype-ideas`；用实际任务验证它与 `assess-options`、各类设计任务的边界。 |
| `improve-codebase-architecture` | 先审视近期频繁变动且维护困难的区域，报告改善候选，再选择要实施的改动。 | 归入 `review-codebase`；实施仍归 `refactor-code`。 |
| `grill-with-docs`、`to-spec`、`to-tickets` | 逐步厘清待决问题，记录稳定术语与决策；将已确定内容整理成规格，再拆成可单独验证且标明阻塞关系的任务。 | 增强 `define-requirements`、`model-domain`、`plan-work`；保存位置按项目需要确定。 |
| `wayfinder` | 对跨会话且路径不清晰的工作维护决策图，先消除关键未知，再进入规格与实施规划。 | 暂作 `assess-options`、`plan-work` 的复杂任务分支。 |
| `handoff`、`ask-matt` 的阶段边界 | 在跨工具、跨目录或跨协作者时传递必要状态，引用已有规格、决策和代码证据。 | 放入 `master` 的按需交接参考；避免复制已有产物，也不把固定会话命令写成通用工程规则。 |
| `diagnosing-bugs`、`code-review` | 缺陷诊断优先建立能捕捉用户症状的反馈信号；审查分别检查项目规范与原始需求。 | 增强 `fix-bugs`、`review-changes`；无法复现时记录已尝试的路径和证据缺口。 |
| `domain-modeling`、`codebase-design`、`writing-for-agents` | 让领域术语、模块设计词汇与供智能体阅读的文档规则各有一个权威来源。 | 作为多个 Skill 共用的按需参考；避免在各 Skill 中复制相同定义。 |

后续优化时重点验证：三项新增任务是否值得独立成 Skill；规格、决策和任务如何沿用项目现有载体；`master` 何时切换能力或保存交接状态。测试先行、密集访谈和外部任务平台均由任务情境决定，不作为所有工程任务的统一前置步骤。

## 从覆盖单元升格为 Skill

一项覆盖任务满足以下条件时，可把英文工作名确定为 Skill 名并创建 `SKILL.md`；创建后的实际效果仍需用真实任务验证：

1. 用户能提出一个明确、可重复的目标，且与相邻候选的触发条件可以区分。
2. 有独特的判断方法、工具顺序或必须保留的工程约束。
3. 能定义独立的产物和验收证据；完成状态不依赖另一 Skill 的笼统结论。
4. 能设计显式触发、自然触发、信息不足和不应触发的案例，以验证后续选择与产物。

未达到条件的覆盖单元继续由 `master` 以常规能力处理，或成为已实现 Skill 的按需参考。已实现项与八项优先候选集中记录在[分类与命名](taxonomy.md)；其余英文标签仅作工作名，不预留目录。
